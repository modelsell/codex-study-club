遇到 `permission denied`、HTTP `403`、`network access`、网络受限或权限审批提示，先判断错误来自哪个工具、发生在哪个阶段，再决定下一步。仅凭 HTTP 403 不足以判断是 Codex 权限问题，也不能据此要求扩大权限。

1. 记录入口与工具：App、CLI、IDE 或 Cloud；分清消息发送、环境准备、工具执行和远端响应。Cloud 的具体入口与适用范围见下方案例。
2. 收集最小只读证据：实际命令、退出码、脱敏错误片段、项目相对路径或公开目标域名，以及发生时间。不要提供密钥、Cookie、Authorization 头、带令牌的 URL 或原始私有日志。
3. 区分审批等待、文件访问限制、DNS/TLS/连接失败和远端 HTTP 响应；证据不足就保留“原因未确认”，不反复运行相同操作。
4. 如果推送、发布或其他外部写操作结果未知，先只读查询目标状态，确认是否已经完成，再判断是否需要重试；不要把没有收到成功回执当作没有发生。
5. 只有确定失败层和必要范围后，才提出最小修改。修正后验证原任务的目标与产物，分别记录命令成功、远端状态和实际可用性。

完整的入口边界、诊断记录和验收步骤见[权限与网络报错案例](/cases/codex-permission-and-network-blocked)。这是一份排查方法，不代表已复现或修复你的客户端故障。
