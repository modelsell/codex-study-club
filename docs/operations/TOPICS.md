## 如何持续维护

- 每日选题前先读本文件和 [BACKLOG](BACKLOG.md)。先查近期一手反馈及已有候选的最新进展，再决定写什么；不要机械重复搜索词或照排期凑文章。
- 痛点检索覆盖 X 中英文、r/codex、OpenAI 开发者社区和 openai/codex Issues。按来源可访问情况记录，不把新闻转述、同一事件跨平台转发当作多个独立反馈。
- 每条候选必须写清：谁遇到什么损失、原始来源和日期、读者能带走什么、如何验收、哪些部分尚未验证。标题随证据调整。
- 区分用户自述、可复现报告、官方回应、本站实测。Issue 状态和标签不等于官方确认根因；浏览量、回复数、Issue 总数不能代表故障发生率。
- 排序考虑阻断程度、独立反馈、可迁移收益和本站验证条件。P1 是编辑优先级，不是热度统计或对故障严重程度的定量结论。
- 状态依次记录为：候选 → 待验证 → 验证中 → 待写作 → 已发布 → 待复核；也可暂缓或淘汰，并保留原因。没有实验结果，不从“待验证”直接写成“有效方案”。
- 每日复盘记录候选推进、失败尝试、来源变化及下一步；每周日重新排序前三项。发布后补稳定 URL、提交、验证范围及独立读者反馈，无数据写不可得。
- 每次调整同步本文件、BACKLOG 和当日复盘。证据台账留在这里，BACKLOG 只保留当前排序，避免多个完整选题清单互相漂移。

## T01：辨别有效推进与空转

- **读者问题**：长时间显示工作中，无法判断该等待还是介入；协调、检查和汇报很多，最终交付却没有完成。
- **来源**：
  - [X：yeu 的等待体验](https://x.com/yeule0/status/2106937732119588946)，2026-10-05 原帖。同日已打开详情核对日期。用户自述为省额度未开 Fast，等待约半小时仍不清楚进展；没有任务日志，不能确认根因。
  - [The Progress Trap](https://community.openai.com/t/the-progress-trap-a-130-packet-case-study-of-long-horizon-codex-reliability/1402423)，2026-10-01。作者报告单个长项目有 130 份过程记录但完整里程碑未验收；本站只读了讨论正文，未审计全部材料。作者明确未证明平台缺陷或故意失控。
- **拟交付**：用文件变化、命令结果、验收项和阻塞证据判断进展；提供保留现场、缩小下一步和明确交付条件的接管模板。
- **验证计划**：选本站一个可安全复现的真实任务，记录初始条件、过程时间线、介入原因及介入前后结果。若没有复现空转，只能发表检查方法，不能虚构“成功救回”。
- **验收**：读者能指出已完成的验收项、未完成项和阻塞点；交付物可独立运行或检查。不把文件数量、消息数量或思考时长当作完成。
- **10-06 交付**：[进展判断方法](/cases/codex-progress-or-loop)，附空白记录表与本站填写示例。以 10-05 公开维护过程说明如何通过新证据修正判断；它是事后整理，不是事前采用模板的对照实验，也未复现模型循环。
- **来源复核**：10-06 重读 Progress Trap 原帖（未审计全部材料），并核对 [Prompting](https://learn.chatgpt.com/docs/prompting) 和 [Long-running work](https://learn.chatgpt.com/docs/long-running-work)。X 原帖本日未再次访问，文章不引用其等待时长作为当前事实。
- **验证范围**：两份 Markdown 经浏览器实际下载、与仓库原文逐字节比对；本地 Lint、构建、63 页/64 目标站内链接通过。桌面与 375px 文章、首页无页面横向溢出；不把发布验收当作纠偏提示词的效果实验。发布提交 [7d49550](https://github.com/modelsell/codex-study-club/commit/7d49550760ef437ca94183b9c6f9dd7553fd9d6b) 的 CI 与 Workers 已成功，生产正文及两份模板已验收；详细证据见 [当日复盘](reviews/2026-10-06.md)。

## T02：模型、强度、速度与额度的取舍

- **读者问题**：想省额度却等得太久；不知道更高强度是否值得，也难以把界面设置与实际消耗对应起来。
- **来源**：
  - [X：undoroid 对速度与稳定性的反馈](https://x.com/undoroid/status/2106931182088892789)，2026-10-05 检索所见，显示为当日相对时间；发表精确时间待复核。它是使用感受，不是可审计性能基准。
  - [Light 标签与滑块困惑](https://community.openai.com/t/new-astra-light-model-in-codex-is-confusing-and-it-costed-me-lot-of-tokens/1402319)，2026-09-30 发布，10-01 有支持账号回应。写作必须包含后续澄清，不能只摘用户对消耗的怀疑。
  - [官方用量说明](https://help.openai.com/en/articles/20001516-managing-usage-with-gpt-6-astra-in-work-and-codex)，2026-10-05 已读取，作为产品规则核对入口；实验时需重新核对。本文不固化价格、倍率或账号可用模型。
- **拟交付**：同一任务的完成时间、可观测用量变化、返工次数和验收结果；给出适用任务范围，而非“全部拉满”或通用最省配置。
- **验证计划**：固定仓库提交、输入和验收；每次独立会话，记录可见模型、强度、Fast 状态及实际环境。排除并发用量干扰，无法隔离时标明。先做小范围对照，依据任务成本决定是否重复；不自动购买额度。
- **验收**：公开成功与失败轮次；用量面板粒度不足则写不可得，不由百分比倒推精确 token 或金额。单次结果不推广成普遍排名，不用生成速度替代任务完成速度。
- **10-07 条件核验**：重读上述 Light 原帖及 10-01 支持账号回复，不以滑块位置推断用量。读取 [Developer settings](https://learn.chatgpt.com/docs/developer-settings) 与 [Usage Insights](https://learn.chatgpt.com/docs/enterprise/usage-insights)；后者是工作区分析说明，不证明本站已取得管理员分析权限。本轮可读取的账户入口返回共享额度窗口，缺少单次任务的精确消耗；未建立隔离并发条件，不能用窗口百分比差计算本任务成本。没有公开账户标识、余额或用量数值。
- **决定**：暂缓模型排名与正式对照，不把测量缺口写成某个模型不划算。10-07 转做已有 CI 文章的证据校订及生成快照只读预检，见 [当日记录](reviews/2026-10-07.md)。没有创建额外模型任务或购买额度。
- **下一步**：只有固定输入、独立轮次和可解释用量同时可得时才恢复对照；此前优先 T03 短交接产物或旧文证据校订。

## T03：跨会话的项目交接

- **读者问题**：换会话后重讲背景、遗漏约束，长项目反复返工。
- **来源**：
  - [上下文共享与 fork 讨论](https://community.openai.com/t/more-useful-context-sharing-by-forking-or-otherwise/1402491)，2026-10-01。报告者明确其异常可能与本机有关，回复中的记忆、fork 解释不能未经官方核对直接变成教程。
  - [GitHub #49211](https://github.com/openai/codex/issues/49211)，2026-09-29。用户报告忽略要求、丢失前文和修改无关代码；缺少本站独立复现，不能据此确认整体模型回归。
- **拟交付**：目标、约束、关键决策、当前提交、已验证事实、未完成项、复现命令构成的交接包；真实续做前后记录。
- **验证计划**：在本站维护任务上建立交接包，让独立的新会话在不读取旧聊天的条件下继续。检查其能否找到相关文件、保持约束并完成剩余验收。若对照失败，保留遗漏项并改模板。
- **验收**：原任务边界得到保留，已完成工作没有重复执行，剩余任务有独立验证。模板不包含密钥、原始用户数据或整段私有聊天。
- **下一步**：先制作短交接模板，用一次真实维护任务检验；没有收益证据时不增加复杂记忆系统。

## T04：不听指令还是消息没送达

- **读者问题**：输入消失、队列未执行或同一请求重复运行，被混称为“不听话”。
- **来源**：[IDE 插件吞消息](https://community.openai.com/t/codex-ide-plugin-silently-eats-messages/1402586)，2026-10-01 发布、10-02 跟帖；[GitHub #50973](https://github.com/openai/codex/issues/50973)，2026-10-04，Windows VS Code 用户报告缺失或重复提交。相似症状不证明同一根因。
- **拟交付**：按“输入是否保留 → 消息是否出现 → 是否启动任务 → 是否执行约束”分流的检查表，以及版本、环境、时间、预期/实际结果和脱敏日志的报告模板。
- **验证计划与验收**：在可用客户端记录正常流程；故障无法复现时只给收集证据的方法，不声称修复。恢复前检查原任务状态，不用连续重发掩盖不确定执行状态。
- **下一步**：重查两个原帖的修复进展，标注客户端及版本范围。

## T05：看懂改动并能撤回

- **读者问题**：看不到清晰差异，原有未提交修改与 Agent 改动混在一起，不敢合并。
- **来源**：[VS Code 差异展示反馈](https://community.openai.com/t/codex-vscode-extension-does-not-show-diffs-which-hinders-development/1396210)，2026-09-09 发布、10-01 跟帖。不能将最近回复日期当作新故障发布日期；评论中的绕过方法未经本站验证。
- **拟交付**：真实但可丢弃的练习仓库，含预先存在的用户改动；演示任务隔离、差异审查和只撤回本次失败改动。
- **验证计划与验收**：以文件差异或哈希证明用户原改动完整保留，失败修改可撤回，最终功能通过验收。危险命令不作为默认恢复方案。
- **下一步**：准备最小练习夹具，避免在生产仓库人为制造损坏。

## T06：更新故障后的工作恢复

- **读者问题**：客户端更新后终端弹窗、焦点被抢或任务无法继续，急需判断影响和恢复路径。
- **来源**：[Reddit：What happened today?](https://www.reddit.com/r/codex/comments/1wq678r/what_happened_today/)，2026-10-05 读取。页面返回相对时间且抓取时间有差异，原帖精确发布日期待核，不按“今天新发生”报道；用户描述 Windows 终端弹窗，评论链接到 [GitHub #48152](https://github.com/openai/codex/issues/48152)（本轮未独立打开该 Issue，属于待核线索）。
- **拟交付**：按版本、系统、症状列明影响、已知修复、临时恢复方式与验证日期。
- **验证计划与验收**：先查原始 Issue 和官方变更记录。社区命令只作为候选，必须核对支持范围并在可控环境验证；没有对应设备时明确未实测。恢复需确认任务、文件和会话现场，不能把重新打开应用当作恢复成功。
- **下一步**：核实当前是否仍受影响；已经修复则写清修复版本，降低新文章优先级，优先更新旧文。

## 优质案例入选标准

案例须展示真实问题、起点、关键失败或调整、交付物和验收证据，让读者能迁移方法。优先有原始作者、代码/演示、适用版本与日期的材料；区分作者声称与本站复现。演示视频、漂亮截图或热门转发本身不足以证明工作流成功。

每条候选后续追加：实验日期与环境、结果、失败边界、文章 URL、提交链接、独立读者反馈和下一轮调整。尚无本站复现或独立读者完成数据，首批六题均不得写成已验证解决方案。
