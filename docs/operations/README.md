# Codex Study Club 日常运营

目标是让更多中文开发者找到教程、完成真实任务并愿意再次使用和贡献。以内容准确性、首次实践成功率和项目稳定性支持自然增长。

## 执行节奏

时区为 Asia/Shanghai。Codex 在现有项目任务中运行，调度由 Codex 定时任务管理；本仓库公开规则与结果，不保存机器凭据。

| 时间 | 工作 | 可交付结果 |
| --- | --- | --- |
| 每天 09:00 | 检查反馈和站点，更新内容，完成最有价值的维护项，验证并提交推送 | 一项实质内容新增或校订；按实际需求完成维护改进；复盘草稿 |
| 每天 20:00 | 独立核验提交、发布状态和可得指标，补漏并复盘 | 当日公开复盘、次日待办排序 |
| 周日 20:00 | 在晚间复盘中加入七日趋势与实验评估 | 下周三项优先工作，不另建重复调度 |

本地定时任务需要机器开机、Codex 应用运行、仓库可用和相应网络权限。漏跑应记录实际时间及原因；补跑先检查当日提交与记录，避免重复内容和重复推送。参考：[OpenAI 官方定时任务说明](https://learn.chatgpt.com/docs/automations?surface=app)（核对日期：2026-09-25）。

## 每次执行流程

1. 查看工作区与远端差异、最近复盘、Issues/PR 和站点状态。保留用户改动；有冲突时用独立工作树，不覆盖工作。
2. 按“阻断使用的问题 → 过时或错误教程 → 新手成功率 → 高价值案例 → 发现和分享体验”排序。当日专注一个主要交付，不为日更制造低价值文章。
3. 内容以读者任务组织：适用人群、前提、步骤、预期结果、失败排查、来源和核对日期。产品新闻说明对读者的实际影响，不照抄发布说明。实测与文档整理明确区分。
4. 优先修正现有页面，避免相同主题重复建页。图片和转载保留归属，遵守 `THIRD_PARTY_NOTICES.md`。
5. 内容或代码改动运行 `npm run lint` 和 `npm run build`；必要时启动本地页面核验链接、正文、元数据。仅改运营 Markdown 时检查链接与 diff 即可。验证失败如实修复或记录阻塞，不把失败的变更作为可发布版本。
6. 仅提交当次改动，普通小改动验证后正常推送。复杂改动、分支受保护或需他人审阅时使用 `codex/` 分支与 PR，不强推、不绕过保护。
7. 查询实际部署状态；提交推送不等于站点更新。生产部署须走仓库已有且已确认的发布流程；没有流程或凭据时记录“部署未确认”，继续交付可完成的工作。
8. 同日更新一份复盘及索引，完成项从待办移出，保留明确的下一步。

## 增长与内容策略

- 首周建立真实基线，优先让新读者完成一次能自行核验的练习，降低贡献门槛。
- 每周至少沉淀一个有验证记录的实战案例，持续修正高访问入口和常见失败路径；选题以真实反馈和官方更新为依据。
- 每周只设一个可衡量的增长假设，例如“更清晰的快速开始能增加教程完成反馈”。写明改动、观测窗口和判断标准；证据不足则继续观察。
- 优先维护 README、内容内链、摘要、分享信息和贡献入口。避免堆关键词、刷 Star、制造虚假用户评价或群发推广。
- 用户反馈可整理成修复和内容待办；未获明确授权，不代表用户发送私信、邮件或跨平台推广。

## 指标口径

| 指标 | 来源与解释 |
| --- | --- |
| Star、Fork | GitHub 当时的计数；记录采样时间。有前期基线才计算净增 |
| Issues、PR | GitHub，分别统计待处理与完成，排除重复记录 |
| 可用性 | 页面实测响应及正文检查；一次成功不能代表全天正常 |
| 内容交付 | 有实质改动且经验证的教程、案例或校订，不以提交次数代替质量 |
| 访问、回访、教程完成 | 仅使用已接入且获准读取的统计；未接入写“不可得”，不凭 Star 推算用户量 |

首周之后用七日趋势调整优先级，不承诺特定粉丝数。没有增长也公开记录。

## 公开复盘

从 [复盘索引](reviews/README.md) 查看每日记录。每份报告包含：目标、完成与未完成、验证证据、提交/PR 链接、部署状态、指标与口径、问题和下一步。读者有用的阶段总结可另外进入 `content/community-updates/`；日常内部流水保留在本目录。

新建或修改许可证、付费采购、赞助政策、密钥与权限、重大删除或不可逆操作需要单独明确授权。常规内容维护、代码修复、验证、提交推送和公开复盘在已授权范围内持续执行。
