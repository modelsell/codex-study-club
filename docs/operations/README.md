## 每次执行流程

1. 查看工作区与远端差异、最近复盘、Issues/PR 和站点状态。保留用户改动；有冲突时用独立工作树，不覆盖工作。
2. 读取并维护[持续选题池](TOPICS.md)，核对 X、Reddit、开发者社区与 GitHub 的近期一手反馈、已有候选进展和官方回应，再同步 BACKLOG 的排序。新选题按 CONTENT-GATE 取得当日官方资料与两个独立需求信号，写明目标读者、实际验证与引入理由。按“阻断使用的问题 → 过时或错误教程 → 新手成功率 → 高价值案例 → 发现和分享体验”选择当日主要交付，不为日更制造低价值文章。
3. 先读 [内容深度标准](EDITORIAL-STANDARD.md)，取得具体材料并对照同类优质原文，成稿逐项做编辑复核；来源数量和 CI 不能替代深度。内容以读者任务组织：适用人群、前提、步骤、预期结果、失败排查、来源和核对日期。产品新闻说明对读者的实际影响，不照抄发布说明。实测与文档整理明确区分。
4. 优先修正现有页面，避免相同主题重复建页。图片和转载保留归属，遵守 `THIRD_PARTY_NOTICES.md`。
5. 内容或代码改动运行 `npm run lint` 和 `npm run build`；必要时启动本地页面核验链接、正文、元数据。仅改运营 Markdown 时检查链接与 diff 即可。验证失败如实修复或记录阻塞，不把失败的变更作为可发布版本。
6. 仅提交当次改动，普通小改动验证后正常推送。复杂改动、分支受保护或需他人审阅时使用 `codex/` 分支与 PR，不强推、不绕过保护。
7. 按 [发布与核验说明](DEPLOYMENT.md) 查询同一提交的检查和实际部署状态；提交推送不等于站点更新。生产部署须走仓库已有且已确认的发布流程；没有流程或凭据时记录“部署未确认”，继续交付可完成的工作。
8. 同日更新一份复盘及索引，完成项从待办移出，保留明确的下一步。

## 增长与内容策略

- 2026-11-08 用户明确要求重新思考定位和改版。采用“产品研究、工作方法、可复现实验”的编辑方向；首页按任务路线、深度选读和成果组织，产品研究页保留历史更新档案。Codex Study Club 的身份、原教程与稳定 URL 保留。编辑索引见 `content/editorial/site.json`，设计依据与页面分工见 [SITE-DESIGN](SITE-DESIGN.md)。这是用户要求与现有内容结构驱动的调整，尚无转化/阅读收益证据。
- 后续选题先决定文章类型与读者成果，再选择产品；每篇连接至少一条相关路线，需要文件的内容同步维护工具包。源码分析、SDK/CLI 实验与客户端实践各按自己的实际证据表达，不把首页推广语当实测结论。

- 2026-11-01 用户补充：不局限 Codex / Claude Code。每天先按真实任务轮换调查一到两类其他 Agent 来源，覆盖团队值守（DeepSeek Harness / Super-agent）、可换模型工具、浏览器自动化、研究/长任务框架等；品牌是观察对象，资料、文件、报表和可审查改动才是交付物。新产品同样过需求与验证门槛，不能只围绕代码故障或热门榜单选题。
- 首周建立真实基线，优先让新读者完成一次能自行核验的练习，降低贡献门槛。
- 优先沉淀有验证记录的完整案例，持续修正有证据的入口问题和常见失败路径；选题以真实反馈和官方更新为依据。条件不足可只研究、补证据或修订旧文，不设每周最低篇数。
- 2026-10-05 起按用户反馈调整为“利他、Codex 使用技巧、优质案例”主线，取代此前创意挑战数量安排。先写清读者的问题和能带走的成果，再选题；首页优先实用案例与学习路径，小游戏和宠物作为补充，不再占据主要更新与推荐位置。
- 按可取得的需求与执行证据安排深度研究、技巧和旧文校订，不设日/周文章配额；质量和实际交付决定是否发布。每篇说明适用人群、前提、可复制提示词/步骤、产物、验收、常见失败和未验证范围。外部案例保留作者、日期、原始链接与代码入口，区分作者报告与本站复现，不将阅读材料写成本站实测。
- 当前选题及证据统一维护在 [TOPICS.md](TOPICS.md)，不预设通用教程目录作为日更任务。优先解决读者的等待、额度浪费、上下文丢失、返工与审查困难；接手仓库、CI、AGENTS.md/Skills 等只在有明确痛点或优质案例时安排。每篇先形成可复用产物与验收证据。纯提示词列表必须有任务和验收示例才发布。创意互动只有能教会可迁移技巧时才继续投入。
- 项目负责人拥有日常产品运营的完整执行权：网站信息架构、首页与导航、视觉样式、版式、响应式适配、交互状态、可访问性、性能和品牌一致性都属于每日维护范围。可依据真实反馈、站点核验和内容策略进行页面改版、组件重构、主题调整与新互动工具建设；改版前写清读者问题与证据，保持稳定 URL，完成桌面、手机和关键交互验证，不为凑更新而改版。
- 创意内容提供可复制提示词、可见结果和验收清单；互动工具实际检查选择、复制、键盘与手机阅读。明确区分工具本身已验证、推荐练习未执行和读者真实反馈，不把测试操作统计为用户参与。
- 每周只设一个可衡量的增长假设，例如“更清晰的快速开始能增加教程完成反馈”。写明改动、观测窗口和判断标准；证据不足则继续观察。
- 优先维护 README、内容内链、摘要、分享信息和贡献入口。避免堆关键词、刷 Star、制造虚假用户评价或群发推广。
- 用户反馈可整理成修复和内容待办；未获明确授权，不代表用户发送私信、邮件或跨平台推广。

## 指标口径

网站统计接入与事件边界见[网站统计口径](ANALYTICS.md)。正式域名已配置主机限定的 GA4 公开兜底 ID；其他域名未配置时关闭。配置与初始化不等于报告接收确认；没有可访问报告时，访问、回访、教程完成与真实收益均记录为“不可得”。

| 指标 | 来源与解释 |
| --- | --- |
| Star、Fork | GitHub 当时的计数；记录采样时间。有前期基线才计算净增 |
| Issues、PR | GitHub，分别统计待处理与完成，排除重复记录 |
| 可用性 | 页面实测响应及正文检查；一次成功不能代表全天正常 |
| 内容交付 | 有实质改动且经验证的教程、案例或校订，不以提交次数代替质量 |
| 访问、回访、教程完成 | 仅使用已接入且获准读取的统计；未接入写“不可得”，不凭 Star 推算用户量 |

首周之后用七日趋势调整优先级，不承诺特定粉丝数。没有增长也公开记录。
